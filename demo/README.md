## Воспроизводимый локальный набор

Миграции создают пустую БД. После запуска общего Docker Compose из корня бэкенда загрузите [seed.sql](seed.sql) **только в локальный контейнер MySQL**:

```bash
docker compose -f docker-compose.yml exec -T db sh -lc 'MYSQL_PWD="$MYSQL_PASSWORD" mysql -u "$MYSQL_USER" "$MYSQL_DATABASE"' < demo/seed.sql
```

Скрипт можно запустить повторно: записи с фиксированными ID не дублируются, а даты приглашения, событий, собраний и опросов сдвигаются относительно дня запуска. Он создаёт дом `8000001`, код `LIG-84-C9`, собственников, нанимателя, организатора, совет дома, админа, ожидающую заявку на вступление, контакты, события, чаты, три формата собраний, активные и завершённый опросы, голоса и заявки всех статусов. Ссылки демо-чатов ведут к боту проекта, настоящие чаты скрипт не создаёт. Файлы не подкладываются: их надо загрузить через API от лица вошедшего пользователя.

Созданные скриптом пользователи имеют отрицательные `max_id` и нужны только для наполнения экранов. **Войти под ними нельзя.** Для проверки API достаточно своего аккаунта MAX и кода дома; для подписки соседа и проверки доставки обоим нужны два разных аккаунта MAX. Отдельные пароли или заранее выданные `initData` не нужны.

## Как получить доступ через MAX

1. Откройте мини-приложение через бота проекта. Возьмите значение `window.WebApp.initData` целиком; не пересобирайте его из полей и не публикуйте. В Swagger Authorize вставьте саму строку, а в HTTP-запросах передавайте `Authorization: Bearer <initData>`. `initData` другого бота не подойдёт.
2. Вызовите `POST /api/init`. `user.id` в ответе — ID вашего профиля. Вызовите `GET /api/houses/search?code=LIG-84-C9` и `POST /api/houses/join` с `code`, `apartmentNumber`, `displayName`, `relationship: "owner"`. Для локального набора возьмите свободную квартиру, например `21`.
3. Из ответа на вступление возьмите числовой `id` заявки. Вызовите `POST /api/debug/houses/approve` с `{"requestId": id}`. После этого `POST /api/init` и `GET /api/houses/me` покажут `membership.status: approved`, роль `resident` и подтверждённую квартиру собственника. Своего аккаунта MAX теперь достаточно для просмотра дома, создания собрания и опроса, голосования и подачи заявки.
4. Для подписки второй человек повторяет шаги 1–3 со своим MAX-аккаунтом и другой квартирой, затем вызывает `PUT /api/requests/{uuid}/subscription` на заявку первого. Переключатель уведомлений должен быть включён у получателей. Смена статуса через `POST /api/debug/requests/status` обновит историю и отправит уведомление с переходом в карточку.

Роль `house_admin` **не появляется от входа через MAX**. Если нужно проверить `GET /api/admin/houses/{houseId}/overview`, после одобрения назначьте её своему членству в локальной БД, подставив `user.id` из `/api/init`:

```sql
INSERT IGNORE INTO house_member_roles (membership_id, role)
SELECT id, 'house_admin'
FROM house_memberships
WHERE house_id = 8000001 AND user_id = <USER_ID> AND status = 'approved';
```

Для серверного дома замените `8000001` на `2`. Такой доступ назначает команда вручную; скрипт не меняет права реальных пользователей MAX. Проверка API и ожидаемые статусы подробнее описаны в Swagger и `DATA-API.yaml`.
